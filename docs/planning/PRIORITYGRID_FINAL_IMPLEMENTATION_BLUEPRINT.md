## 1. Executive summary

PriorityGrid is a **locally hosted, offline decision console** for a *simulated* six-service campus/clinic network. A Python backend owns one authoritative state. It generates reproducible synthetic electrical telemetry, **diagnoses** what the evidence supports (shortage, demand surge, voltage-proxy sag, estimated thermal stress, feeder interruption, sensor failure, stale/missing observations, radio-link loss, or "not enough evidence"), converts the diagnosis into explicit **constraints**, and **allocates** limited capacity across critical (T1) and non-critical (T2, T3) services with a lexicographic constrained optimizer (OR-Tools CP-SAT, independently checked against exhaustive enumeration of all 64 masks). The result is validated, applied **in the model only**, sent over USB → ESP32 gateway → **ESP-NOW** to real LEDs, and **confirmed by a firmware acknowledgement carrying the mask actually applied**. Everything is explained, persisted, replayable and recoverable in tier order.

What changed relative to the three source documents:

1. **One electrical truth: simulated.** BM's physical ADC/shunt bus emulator is dropped from the MVP (§4, C1). The two potentiometers and four buttons are **real physical inputs that drive the simulation**; they are never presented as sensors. BM's valuable mathematics (demand factor `g`, supply-sag factor `ρV`, static thermal derating `cdfT`, the evidence adapter) is kept — fed by the simulator instead of ADCs.
2. **Hardware matches the real inventory** from the master prompt: 2 ESP32, 2 pots, 4 buttons, 6 LEDs, 10×220 Ω, 10×10 kΩ. No OLED, LCD, third board, relay, or buzzer is assumed (MP/UP assumed some).
3. **Optimizer is CP-SAT primary + exhaustive-enumeration oracle on every plan**, with disagreement → oracle wins and is logged. A fresh run on 3,000 random contexts showed **0 mismatches, 0 constraint violations, 3,000/3,000 `OPTIMAL`** [VERIFIED-DT].
4. **A finding that changes the pitch:** on this six-service catalog a *smaller-demand-first greedy* baseline is already optimal in service quality in 30,000/30,000 random contexts [VERIFIED-DT] (a known property: with equal weights and one binding capacity limit, ascending-demand greedy maximises count). Fixed-order greedy lost on T2 count in 123/30,000 (0.41 %). **Do not claim "the optimizer beats greedy."** The defensible value is *guaranteed feasibility, a proven tier policy, reason codes, and extensibility* — and the benchmark must include a stress catalog (§31) where heterogeneous weights make greedy fail (0.4–1 % of random contexts [VERIFIED-DT]).
5. **Anti-oscillation is demonstrated, not asserted:** with capacity dithering ±300 W every second for 60 s, a naive re-solve-every-tick controller made **61 switch transitions**; the designed controller (Schmitt quantisation + 4 s stability window + 3 s dwell + one-ON-per-second) made **3** [VERIFIED-DT].
6. **Honesty guardrails are structural:** provenance tags on every value, three separate failure-domain fields (electrical / evidence / link), `unknown ≠ 0`, heuristic scores never shown as probabilities, hardware "confirmed" only on a matching firmware ACK.

**The one loop that must work:** physical knob/button → simulated electrical state → detection → diagnosis → constraints → priority optimization → independent validation → modeled shedding → ESP32 command → firmware-confirmed LED → dashboard explanation → event log → staged, tier-ordered recovery.

## 2. Difference between the two concepts

| Dimension | BLACKOUT MESH | PriorityGrid | In the final product |
|---|---|---|---|
| Question answered | "Is something wrong, and what kind?" | "Given what's wrong, which services keep running, and why?" | Both, in one pipeline |
| Output | Alarm / simulated trip | Per-service served/shed plan with reason codes | Plan + ladder + explanation |
| Strength | Multi-signal evidence, trust gating, FSM, comm-vs-power separation, reproducible fault injection | Topology, tiers, hard capacity/feeder constraints, optimization, staged restoration | BM = *fault-intelligence & link-health subsystems*; PG = *decision engine* |
| Electrical data | Physical bus (ADC) in BM v2.0 | Simulated | **Simulated** (+ physical knobs) |
| Failure mode if used alone | Detects but cannot decide who loses power | Optimizes on unexamined inputs (garbage-in) | Diagnosis gates what the optimizer is allowed to believe |

Coupling point (the "decision-engine-level" integration required by the prompt): **BM-derived diagnosis never talks to the optimizer directly.** It produces a typed `Diagnosis`; the **Evidence Adapter** (§17.6) converts it to a `ConstraintSet`; the allocator consumes only that. One state, one adapter, no second opinion.

### 4.2 Rationale cards for the important conflicts

Format: **(1) Disagreement · (2) Why it matters · (3) Chosen · (4) Why best for 24 h · (5) Deferred.**

**C1 — Measured vs simulated electricity.**
(1) BM v2.0 builds a real low-voltage bus with ADC channels; MP D-002 and UP choose pure simulation. (2) The prompt's *hardware truth boundary* forbids presenting pots as sensors; building the BM circuit also consumes H2's first 6+ hours and BM itself rates feasibility 5.5/10. (3) Simulation, with knobs/buttons as honest `PHYSICAL_INPUT`. (4) Removes calibration, ADC-noise flapping and a whole failure class; keeps the real parts that matter to judges (radio, ACK, LEDs). (5) BM circuit and C1–C6 calibration stay as a future *measured-evidence adapter* behind the same `Observation` schema.

**C4 — Are critical loads hard constraints?**
(1) UP offers `x_i=1` for T1 + `CRITICAL_INFEASIBLE`; BM keeps them in the objective. (2) With hard constraints an infeasible case returns *nothing*, so no allocation, no explanation, no LED update. (3) Lexicographic dominance: T1 count, then T1 importance, then T2, T3. [VERIFIED-DT: at 2,500 W → only L0, L1 reported `CAPACITY`; at 0 W → nothing, L5, both `SOURCE_UNAVAILABLE`.] (4) Always yields a valid plan and explainable shortfall. (5) Hard "must-serve" mode is a config flag for a production variant.

**C5 — Severity vs criticality.**
(1) UP's FSM has a `CRITICAL` state; the prompt forbids using one word for two ideas. (2) A judge hearing "critical fault on a critical load" will assume they are the same field. (3) Two enums, two UI chips: `severity ∈ {INFO,LOW,MEDIUM,HIGH,SEVERE}` and `tier ∈ {T1,T2,T3}`; `CRITICAL` is only ever used as the English name for T1 *services*. (4) Zero cost, removes a class of Q&A traps. (5) —

**C6/C9/C12 — Where does protection and intelligence live?**
(1) BM sheds on the ESP32 from measured evidence; prompt/UP/MP say shedding is simulated and ESP32s are indicators. (2) Without physical sensing the ESP32 has nothing to shed *from*; claiming otherwise misleads. (3) Backend decides; ESP32s display, hold last state, and show `UNKNOWN` when the host is stale. A knob-driven, shed-only lookup-table fallback is a P2 feature explicitly labelled `LOCAL_FALLBACK (knob-driven; no diagnosis)`. (4) Smaller firmware, no dual-implementation parity risk in the MVP. (5) BM's `permitted_mask ∧ host_mask` edge policy and `POLICY_MISMATCH` parity events.

**C10/C11 — Radio protocol and acknowledgement.**
(1) UP's 18-byte struct lacks session/boot/state-revision; BM's v2 has them but also physical telemetry types. (2) Prompt requires protocol version, command ID, session/boot ID, sequence, requested mask, state revision, time identifier; and ACK must carry the *applied* mask. Espressif's documentation describes the send callback as transport status and recommends application-level ACK and retransmit on timeout (§32). (3) BM-style 16-byte header, new payloads (§12). (4) Same reliability model, fewer message types. (5) `CONTEXT`, `TELEM`, encryption (P1 optional).

**C14 — Which solver is "primary"?**
(1) BM runs enumeration live and CP-SAT as cross-check; UP the reverse. (2) The prompt demands a *genuine* use of OR-Tools and an independent validator, and forbids claiming optimality unproven. (3) CP-SAT solves 4–6 sequential lexicographic stages; each stage's status must be `OPTIMAL` to claim "optimal under policy"; the 64-mask enumerator then re-derives the answer. On disagreement the **enumerator's** answer is used and a `SOLVER_DISAGREEMENT` event is logged. Measured design-time: CP-SAT p50 2.6 ms, p95 4.1 ms; enumerator p50 0.3 ms (sandbox CPU, not your laptop) [VERIFIED-DT]. (4) Cheap, exact, defensible. (5) Larger catalogs: CP-SAT alone (enumeration is 2^N).

**C15 — Restoration parameters and the reserve margin.**
(1) UP: reserve ≥5 % or ≥3 kW; BM: none. (2) A 5 % reserve at exactly 14 kW would permanently block the final restore; 3 kW is 21 % of our whole supply. (3) Inputs are Schmitt-quantised (capacity 100 W step ±50 W; `g` 0.05 step ±0.03), 16-tick stability window, 12-tick dwell, 4-tick interval. Verified: full recovery from "only L0" at 14 kW restores L1 at 4.0 s, then L2, L3, L4, L5 at 5.0–8.0 s; 61 → 3 transitions under dither [VERIFIED-DT]. (4) Demo-friendly (8 s end-to-end) and stable. (5) Per-service minimum-on time, solver-aware reserve.

**C16 — Temperature.**
(1) BM: dynamic `T_est` displayed, **static** derating used; UP: optional first-order model. (2) A thermal state that depends on served load, fed back into capacity, creates shed→cool→restore→heat limit cycles. (3) Decisions use steady-state allowed loading `cdfT = min(1, √(max(0, T_warn−T_amb)/(ΔT_rated·κ)))`. Check: T_amb 55 °C, κ 1.8 → 0.657; 55 °C, κ 1 → 0.882; 30 °C → 1.0 [VERIFIED-DT]. Dynamic `T_est` and predicted `T_post` are `ESTIMATED` display values. (4) No feedback loop to debug. (5) Dynamic thermal escalation.

**C17 — Confidence.**
(1) Three different notions (`anomaly_pct`, `score`, "ranking"). (2) A bounded heuristic is not P(fault); judges will ask. (3) `ranking_score`, `margin`, `coverage`, `status` (§18); "calibration" only if a reliability curve is actually computed on held-out seeds. (4) Cheap, honest. (5) Calibrated probabilities.

**C21 — Replay.**
(1) BM: P2; MP/UP: P1. (2) With BM's physical bus gone, *all* inputs are events (scenario script, knob values, button presses, injections) stamped with a control tick. (3) Event-sourced replay: feed the stored input log back through the pure pipeline with the same seed → identical decisions (radio timings excluded). (4) Cheaper than the physical-window replay BM feared. (5) Interactive scrubbing UI.

**C23 — Hardware inventory.**
(1) MP/UP: 2–3 ESP32 + LCD/OLED, *no* pots; prompt: 2 ESP32, 2 pots, no displays. (2) Wiring plan, LED count and demo script depend on it. (3) Prompt inventory is law (hierarchy #1). Displays and a third board are **not** dependencies. (4) —(5) Third board for two remote LED banks; OLED.

**C27 — Held-out testing.**
(1) Seed ranges differ. (2) BM correctly notes a new RNG seed alone is not "held-out". (3) Tune on seeds 0–19, freeze thresholds/policy, evaluate on 100–119, and include one *unseen topology* (UP's seven-load tree) plus perturbed demands/timings. (4) Meets "scenarios not used during tuning". (5) External/third-party scenarios.

## 5. Final product definition

**PriorityGrid** is a decision-and-control application for a facility operator. It is not a dashboard that happens to have a fault panel; every screen element serves one of seven verbs: **Detect, Diagnose, Prioritize, Optimize, Act, Explain, Recover.**

**Scope boundary (the "truth boundary").**

| Real in the prototype | Simulated / modeled in the prototype |
|---|---|
| Embedded execution on two ESP32 boards | Source capacity, feeder state, per-service demand |
| ESP-NOW packets, retries, ACKs, heartbeats, latency, loss | All voltage/current/demand/temperature values |
| Knob (pot) and button input | Feeder contacts, sensor faults, observation loss |
| LED states driven by firmware | Load shedding and restoration (the *effect*) |
| Python algorithms: detection, diagnosis, optimization, validation | "Protection" and "tripping" |
| Event log, replay, benchmark generation | Any "kilowatt delivered/removed" |

**Provenance tags (every value shown or stored carries one).** The six mandated tags plus two additions required by the source documents:

| Tag | Meaning | Example |
|---|---|---|
| `SIMULATED` | generated by the simulator | `src.cap_w`, `fdrA.v_pu` |
| `PHYSICAL_INPUT` | read from a real knob/button | `pot_a_raw`, `btn_events` |
| `DERIVED` | computed from tagged inputs | `g`, `ρV`, `cdfT`, feature residuals |
| `ESTIMATED` | model output with stated assumptions | `T_est`, `T_post` |
| `MODELED` | effect of an action in the simulator | `served_w`, shed set |
| `PHYSICAL_INDICATOR` | firmware-confirmed GPIO state | `confirmed_mask` |
| `LINK_MEASURED` *(added)* | real radio/serial measurements | RTT, loss, heartbeat age |
| `REPLAY` *(added)* | re-executed or played-back history | any value in a replay view |

Rule: a `MODELED` decision is never labelled as proof that power was delivered or removed. An LED is a `PHYSICAL_INDICATOR` of a *simulated* decision.

## 6. Problem statement

Small facilities and campuses face supply shortfalls, section interruptions, noisy or missing telemetry, and failing communications — often at the same time. A monitor that raises an alarm leaves the operator to decide, under pressure and with uncertain data, **which services to keep, in what order, and whether the data can be trusted**. PriorityGrid demonstrates that decision loop end-to-end on a simulated six-service network: it diagnoses the cause with explicit uncertainty, separates electrical, evidence-quality and communication problems, optimizes a feasible priority-ordered allocation under hard source and feeder limits, executes it in the simulation with real wireless indicator hardware that acknowledges what it applied, explains the trade-offs, and restores service in a controlled order. It is a proof-of-concept; it does not sense, switch or protect real mains.

## 7. Intended users and operational workflow

**Primary persona:** campus/clinic facility operator (judge plays this role in the demo). **Secondary (future):** rural-microgrid technician, small-plant maintenance lead.

**Operator workflow (all screens support it):**

1. **Observe** — Overview strip shows capacity, demand, served, shed, T1 services served `n/2`, ladder level, link status.
2. **Understand** — Diagnosis card: hypothesis, evidence for/against, missing evidence, status (`CONFIRMED / AMBIGUOUS / INSUFFICIENT`), severity.
3. **Decide** — Allocation card: selected set, binding constraints, per-service reason, critical shortfall with reason code, greedy comparison.
4. **Act** — `AUTO_SIM` applies the validated plan to the model; `RECOMMEND_ONLY` waits for the operator's *Approve*.
5. **Confirm** — Three masks side by side: **Requested** (plan) / **Modeled** (applied in simulation) / **Indicator** (firmware-confirmed LEDs).
6. **Recover** — Recovery gate panel shows what blocks restoration and the countdown; services return T1 → T2 → T3, one per second after the stability window.
7. **Review** — Incident timeline; deterministic replay; exported results.

Operators can also *inject* events (dashboard or physical buttons). Injection controls are labelled **"Inject synthetic event"**.

### 8.2 Authoritative state and concurrency [SPEC]

* **One Python process, one control loop, one writer of grid state.** Mutations (dashboard, knobs, scenario script, injections, hardware events) enter a bounded `asyncio.Queue`; the loop drains it once per tick.
* Each tick yields an **immutable `SystemSnapshot(snapshot_seq, control_revision, tick, …)`**. `control_revision` increments only when the applied mask or an operating constraint changes.
* The solver runs in a thread executor. When it returns, the executor **re-checks `control_revision`**; if it changed, the plan is discarded and logged `STALE_PLAN` (never applied).
* **Truth isolation:** the simulator holds `WorldTruth` (true capacity, true feeder state, true sensor faults). The pipeline sees only `Observation` objects. A test asserts the `diagnosis/` and `control/` packages cannot import `simulation.truth` (§30, T-LEAK).
* **React never simulates.** It renders snapshots and posts typed requests (`request_id`, `expected_control_revision`).

### 8.3 Per-tick order (exact)

1. Advance the control clock (frozen while `PAUSED`) and apply queued external events (knobs, buttons, dashboard, scenario-script steps).
2. Simulator advances `WorldTruth`; generate **observations** (independent seeded noise stream per channel; optional stale/missing/stuck/bias faults) — origin `SIMULATED`.
3. Validate samples → channel trust → baseline/anomaly features → detection FSM.
4. Rank hypotheses → diagnosis (status, score, margin, severity, evidence).
5. **Evidence Adapter** → `ConstraintSet`.
6. If constraints changed or a restoration step is due: solve (CP-SAT) → verify (enumeration) → validate.
7. Executor checks preconditions (revision, mode, dwell, stability, reachability) → applies to the **model** (`MODELED`) → compiles `SET_MASK`.
8. Hardware worker sends/retries; ACKs update the *indicator* mask separately.
9. Persist events/decisions; publish snapshot (≤4 Hz) and event deltas.

### 8.4 Clocks and rates

| Item | Value [SPEC, tunable] |
|---|---|
| Control tick | **250 ms** (4 Hz); all windows in ticks |
| Snapshot to browser | ≤ 4 Hz; charts decimated |
| Heartbeat (each node → host) | 1 Hz; **stale** at 3 s, **offline** at 10 s |
| Knob/button frame (N1) | ≤ 10 Hz on change; 1 Hz keep-alive; **stale** at 2 s |
| Simulated observation freshness | stale after 12 ticks (3 s) |
| ACK | retry at 200 ms, ≤2 retries, timeout 600 ms |
| Solver budget | 150 ms total [TARGET]; design-time p95 was 4.1 ms on a sandbox CPU — **re-measure on the demo laptop** |

Fast-protection claims (milliseconds) from BM are **not carried over**; this is a simulated, ≈4 Hz decision system.

### 9.3 What the hardware proves — and does not

* **Proves:** two real peers exchange versioned packets; a command can be rejected as stale/duplicate; a reboot is detected; a link outage is visible; an ACK carries the applied state; physical inputs reach the model.
* **Does not prove:** that power flowed or stopped; that an LED actually lit (firmware confirms the GPIO it drove — judges can *see* the LED, but the software cannot); multi-hop mesh routing (two peers = direct link).

### 10.4 Electrical sanity checks (arithmetic, not measurement)

* LED current ≈ (3.3 V − V_f)/220 Ω: red (V_f ≈ 1.9 V) ≈ 6 mA; green (≈2.1 V) ≈ 5 mA; blue/white (≈3.0–3.2 V) ≤ ≈1.4 mA (**will be dim** — put blue/white LEDs on non-critical positions or accept dimness). Well below per-pin limits.
* Pot at 3.3 V across 10 kΩ draws ≈0.33 mA.
* 3.3 V logic only. **Nothing touches mains. Nothing 5 V touches a GPIO.** The two boards need **no common wire** for ESP-NOW.
* Label every LED with tape: `L0 CLINIC T1`, `L1 EMERG LIGHT T1`, `L2 PUMP T2`, `L3 COMMS T2`, `L4 COLD T2`, `L5 COOLING T3`. Colour is cosmetic; text carries the meaning.
* If a button/pot is unplugged the system must keep running (§25.4, §38).

## 11. Physical-control mapping

All physical controls are `PHYSICAL_INPUT`; the simulator turns them into **events** (they are recorded in the input log, enabling deterministic replay).

| Control | Mapping | Quantisation / conditioning |
|---|---|---|
| **POT_A** | **Source capacity** `C_src` = 0 … 14,000 W (nominal at full CW) | 12-bit ADC, 11 dB attenuation, median of 16 samples at 100 Hz, 3 % dead zone at each end, **100 W steps with ±50 W Schmitt** |
| **POT_B** | **Demand factor** `g` = 0.50 … 2.00 | same filter; **5 % steps, ±3 % Schmitt**; tape marks at `g = 1.00` (≈ 1/3 travel) |
| **BTN1** short | Toggle **Feeder A open** (sim event) | 30 ms debounce, edge on release |
| BTN1 long (1.5 s) | Toggle **Feeder B open** | |
| **BTN2** short | Toggle **supply-voltage sag** (`ρV` truth 0.60) | |
| BTN2 long (1.5 s) | Toggle **cooling loss** (`κ` 1.0 → 1.8) | |
| **BTN3** short | **Operator ACK** (clears a latched incident) | |
| BTN3 long (2 s) | Toggle **RADIO MUTE** on #1 (real comm fault: stops TX/RX application frames) | works locally even when muted |
| **BTN4** short | **RECOVER**: clear all injected faults (scenario `RECOVER`, not a run reset) | |
| BTN4 long (3 s) | **RESET RUN** (new run + new device session) | |

**Control arbitration (explicit, never silent).** Each parameter (`C_src`, `g`) has a `control_source ∈ {KNOB, DASHBOARD, SCRIPT}` shown in the UI. A dashboard write overrides the knob; the knob regains control only after it moves > 4 % from where it sat at override time ("soft takeover"). If knob frames are stale (> 2 s) or the ADC is implausible (value jitter > 8 % over 1 s while untouched, or pinned at a rail), the input is flagged `INPUT_INVALID`, control reverts to `DASHBOARD`, and a banner says so. A floating wiper is therefore detected *heuristically* — there is no hardware disconnect-detect on the wiper.

## 12. ESP-NOW architecture

**Topology:** one direct unicast pair, fixed Wi-Fi channel (default 1), STA mode, no router, peers preconfigured by MAC (peer allow-list in git-ignored `secrets.h`). **Not a mesh.**

### 12.1 Why application ACKs

Espressif's ESP-NOW documentation limits the payload to 250 bytes, lists several reasons a send can fail, recommends sending the next frame only after the previous send callback has returned, and recommends application-level ACK data with retransmission on timeout (source in §32). The send callback tells you about the **transmission attempt**, not that the receiver parsed the packet or drove a GPIO. PriorityGrid therefore treats the callback as `transport_ok` and requires an application `ACK` for "confirmed".

### 12.2 Frame layout (little-endian, explicit field-by-field serialisation — never `memcpy` a struct across the wire)

```
Header (16 B):  magic u8=0xA7 | ver u8=1 | node_id u8 (0=host,1=FIELD,2=GATEWAY) | type u8
                session u32 | boot_id u32 | seq u32
Trailer (2 B):  CRC-16/CCITT-FALSE (poly 0x1021, init 0xFFFF) over header+payload   [check("123456789") = 0x29B1]
```

| Type | Dir | Payload | Size |
|---|---|---|---:|
| `1 HELLO` | node→host | `fw_ver u16, role u8, bank u8` | 22 |
| `2 SYNC` | host→node | `new_session u32, expected_boot u32` | 26 |
| `3 SET_MASK` | host→N1 | `cmd_id u32, state_rev u32, host_tick u32, req_mask u8, alert_mask u8` | **32** |
| `4 ACK` | N1→host | `ack_cmd_id u32, applied_mask u8, applied_alert u8, status u8, fw_state u8, applied_state_rev u32` | **30** |
| `5 HEARTBEAT` | node→host | `uptime_ms u32, applied_mask u8, applied_alert u8, link_state u8, flags u8, rx_ok u16, tx_fail u16` | 30 |
| `6 INPUT` | N1→host | `pot_a u16, pot_b u16, btn_level u8, btn_events u8, flags u8, applied_mask u8, applied_alert u8, rsv u8` | 28 |
| `7 PING` / `8 PONG` | both | `ping_id u32, t_host_ms u32` | 26 |

Largest frame 32 B ≪ 250 B. `req_mask`/`alert_mask` are global 6-bit masks (bit *i* = service L*i*); bank A uses bits 0–2.

**`ACK.status`**: `0 APPLIED`, `1 DUP_REPLAY` (duplicate `cmd_id`: cached ACK re-sent, no side effect), `2 REJ_SESSION`, `3 REJ_BOOT`, `4 REJ_STALE_REV`, `5 REJ_BAD` (CRC/length/`alert_mask` ⊄ ¬`req_mask` etc.), `6 REJ_MUTED`.
**`fw_state`**: `0 BOOT, 1 UNSYNCED, 2 ONLINE, 3 LINK_STALE, 4 MUTED`.

**Verified example frames [VERIFIED-DT — generated with the CRC above]:**

```
SET_MASK  (session 12, boot 0x00015A27, seq=cmd_id=4021, state_rev 42, tick 8400, req=0b011011 (L0 L1 L3 L4), alert=0)
a7 01 01 03 0c 00 00 00 27 5a 01 00 b5 0f 00 00 b5 0f 00 00 2a 00 00 00 d0 20 00 00 1b 00 db 8f
ACK       (same session/boot, ack_cmd_id 4021, applied_mask 0b000011 (bank A: L0 L1), status APPLIED, fw_state ONLINE, rev 42)
a7 01 01 04 0c 00 00 00 27 5a 01 00 d1 03 00 00 b5 0f 00 00 03 00 00 01 2a 00 00 00 11 f6
```

(Bank A applies bits 0–2 of `req_mask` = `0b011` → L0, L1 on, L2 off; the host composes the global confirmed mask with bank B's local read-back.)

### 12.3 Session, boot, duplicate and stale rules

* **`session`** — host counter persisted in SQLite; incremented on each run start, reset and backend restart; never wraps (exhaustion ⇒ forced re-init).
* **`boot_id`** — random `u32` drawn by each node at boot; binds `session ↔ boot` at `HELLO/SYNC`. A changed `boot_id` = **reboot detected** → host discards pending commands for that node, sends `SYNC`, then the latest plan.
* Node rejects: wrong magic/ver/length/CRC, unknown MAC, `session` older than current (`REJ_SESSION`), `boot` mismatch (`REJ_BOOT`), `state_rev` older than the last applied in this session (`REJ_STALE_REV`). A **newer** session is accepted only through `SYNC`; a stale `SYNC` can never downgrade an active session.
* **Duplicates** (same `cmd_id`): resend the stored ACK, do not re-apply.
* **Never block in the radio callback:** callbacks only enqueue; the main loop validates and drives GPIO.
* **Optional hardening (P1):** ESP-NOW PMK/LMK (16-byte keys) from `secrets.h`. CRC is corruption detection, **not authentication**; the MAC allow-list is the MVP access control.

### 12.4 LED state encoding (applied identically on both banks)

| Pattern | Meaning | Source |
|---|---|---|
| **Solid** | served, mask confirmed applied | `req` bit 1, `alert` bit 0 |
| **Off** | shed (allocator decision), confirmed | `req` 0, `alert` 0 |
| **4 Hz blink** | **unavailable / alert** — feeder open, source unavailable, or a **T1 service lost** | `req` 0, `alert` 1 |
| **1 Hz blink** | **unknown / unconfirmed** — unsynced, host stale, node muted; applies to services last known ON | node-local state |
| Boot | lamp test (each LED 300 ms) then **1 Hz blink on all** until `SYNC` | node-local |

`req ∧ alert ≠ 0` is invalid (`REJ_BAD`). Onboard LED (GPIO2, after boot): 1 Hz = healthy, 4 Hz = host/peer stale, off = uninitialised. **A fast-blinking L0/L1 LED = a critical service has been lost.**

### 12.5 Heartbeat, link states and what each does

| Link state (per node) | Condition | Dashboard | Effect on electrical model |
|---|---|---|---|
| `ONLINE` | heartbeat < 3 s, ACKs current | green | none |
| `DEGRADED` | loss > 20 % over last 20 frames or RTT p95 > 100 ms *[thresholds UNVERIFIED]* | amber | none |
| `STALE` | no heartbeat 3–10 s | amber/unknown | none; indicators `UNCONFIRMED` |
| `OFFLINE` | no heartbeat > 10 s | red | none |
| `UNSYNCED` | `boot_id` changed / new session | grey | none; resync |
| `MUTED` | node reports `fw_state=4` | grey | none |

**Hard rule (T08/T-DOMAIN):** no link state ever opens a feeder, changes `C_src`, or changes any service's `served` flag in the model.

## 13. USB serial protocol

One **UTF-8 JSON object per line**, `\n` terminated, **max 512 bytes/line**, 115200 baud (a ≈150-byte line ≈13 ms on the wire). Oversized, non-JSON or schema-invalid lines increment `gw_stats.bad` and are dropped — they never raise an exception into the control loop. The reader is a dedicated thread with a bounded queue (never on the asyncio event loop).

**Host → gateway**

```json
{"v":1,"k":"cmd","cmd_id":4021,"session":12,"seq":4021,"state_rev":42,"tick":8400,"req":27,"alert":0}
{"v":1,"k":"sync","session":13}
{"v":1,"k":"ping","id":77}
```

**Gateway → host**

```json
{"v":1,"k":"hello","node":2,"boot":88231,"fw":"1.0.0"}
{"v":1,"k":"ack","via":"RADIO","node":1,"cmd_id":4021,"applied":3,"alert":0,"status":0,"rev":42,"rtt_ms":18}
{"v":1,"k":"ack","via":"LOCAL","node":2,"cmd_id":4021,"applied":24,"alert":0,"status":0,"rev":42}
{"v":1,"k":"input","node":1,"pa":3120,"pb":1495,"bl":15,"be":1,"fl":0}
{"v":1,"k":"hb","node":1,"up":43129,"am":3,"aa":0,"ls":2,"rx":1210,"txf":2}
{"v":1,"k":"gw","lost":0,"dup":0,"bad":0,"age_n1_ms":220,"rssi":-42}
{"v":1,"k":"err","code":"REJ_STALE_REV","cmd_id":4020}
```

(`applied` for node 2 is the **global** bits it controls, `24 = 0b011000` = L3, L4.)

**Fake gateway for development.** `tools/fake_gateway.py` implements the same protocol, tags every message `"virtual":true`, and the dashboard shows `VIRTUAL` in the hardware panel. **Virtual ACKs never count toward radio statistics or acceptance tests.**
